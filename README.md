## 开发与构建

Flutter 固定为 `3.47.4`，使用其自带 Dart `3.13.3`；Go `1.24.1+`、Python `3.10+`。SDK 版本由 `pubspec.yaml` 的 `environment.flutter` 统一声明，Windows 构建脚本先检查版本，GitHub Actions 从同一字段读取。版本不符时需手动切换 SDK，脚本不安装或升级环境。Android 需要 JDK 17、SDK 36、NDK `28.2.13676358`；Windows 需要 Visual Studio C++ 桌面组件及 MinGW-w64 x64；iOS 需要 macOS、完整 Xcode 和 CocoaPods。

构建脚本对子进程默认设置 `GOPROXY=https://goproxy.cn,direct`、`GOSUMDB=off`，同名环境变量可覆盖。

GoLand 直接运行 `native` 模块不会继承构建脚本的子进程设置。若下载依赖时连接 `proxy.golang.org` 超时，可以在本机终端执行下面的 Go 配置，再重新运行原构建配置。这里只更改当前 Windows 用户的 Go 模块下载源，不改系统网络代理；IDE 或终端显式设置的 `GOPROXY` 环境变量优先。`|` 允许下载源遇到超时等错误时继续尝试后续来源；依赖版本、TLS 证书验证和 Go 默认校验和验证保持不变。

~~~powershell
go env -w "GOPROXY=https://goproxy.cn|https://proxy.golang.org|direct"
go env GOPROXY GOSUMDB
~~~

原本未持久设置 `GOPROXY` 时，可用 `go env -u GOPROXY` 恢复 Go 默认设置；原本有自定义值时应恢复原值，不要关闭校验和验证来处理网络超时。`native/bridge` 是原生桥接入口，不是 Flutter 窗口程序；正常客户端仍通过 Windows 构建脚本生成。

~~~sh
python3 scripts/build_android.py                 # 红果赏
python3 scripts/build_android.py --all-sources   # 真果赏
python3 scripts/build_android.py --abi arm64-v8a
python3 scripts/build_android.py --cn-mirrors    # 国内镜像
~~~

~~~powershell
.\scripts\build_windows.ps1
.\scripts\build_windows.ps1 -AllSources
.\scripts\build_windows.ps1 -ChinaMirrors
.\scripts\build_windows.ps1 -Run
.\scripts\build_windows.ps1 -ChinaMirrors -Run
.\scripts\build_windows.ps1 -ChinaMirrors -Run -DisableRemoteImages
.\scripts\build_windows.ps1 -ChinaMirrors -AllSources -Run -DisableRemoteImages
~~~

Windows 脚本依次执行 SDK 版本检查、Go 原生核心编译、`flutter pub get --enforce-lockfile`、Release 构建和完整可运行目录导出；加 `-Run` 后仅在上述步骤全部成功且锁文件恢复后启动导出目录内的客户端。加 `-Archive` 可额外生成 ZIP（CI 使用），本地默认不压缩。Go 工具链固定使用本机安装，缺少或版本不足时应手动处理，不自动下载 Go SDK。若已设置 `HTTP_PROXY` 而未设置 `HTTPS_PROXY`，构建子进程沿用现有代理下载 HTTPS 原生依赖，不改系统代理。`-DisableRemoteImages` 仅用于无远程海报的开发验证，普通构建无需添加。默认版与 `-AllSources` 版仍分别对应红果赏、真果赏。

`pubspec.lock` 纳入源码并固定依赖版本及校验值。国内镜像模式只临时切换包源地址，兼容 LF / CRLF 换行，结束后按原始字节恢复锁文件，不自动升级依赖；无需额外的本地依赖快照或手工替换 `.dart_tool` 配置。需要调整依赖时，使用固定 SDK 有意更新并检查锁文件，再运行严格锁定构建。

**内置更新地址**：[GitHub Releases](https://github.com/starsw001/hongguo-win-public-package/releases)。关于 → 检查更新。公开版本标签使用 tag主版本.次版本.修订号，例如 tag1.1.29；客户端按数字比较已发布版本（含该格式的预发布，不含草稿），构建号从本款软件已验签的清单读取。ZIP 与签名清单缺一不可，不能只传 ZIP。

**你以后发版**：
1. 修复后递增 pubspec.yaml，例如 1.1.28+159。按原流程构建两版，沿用原分发编号和签名身份；核对故障剧集的播放及下载。不要上传源码备份、已使用的程序目录、私钥、账号或视频。
2. 在本项目根运行 `python scripts/release_windows_updates.py`，从当前版本已签名运行目录生成两个 ZIP、两个 Ed25519 更新清单到 dist/windows/releases/v<版本>。可用 --edition 只选一款，签名资料路径可显式指定。已有发布文件不会覆盖。正常开发构建不额外生成 Windows ZIP；--archive 也能生成对应签名资产。
3. 在指定 GitHub 仓库创建正式 Latest Release，例如标签 tag1.1.29，上传 hongguoshang-1.1.29-build160-windows-x64.zip、hongguoshang-windows-x64.update.json、zhenguoshang-1.1.29-build160-windows-x64.zip、zhenguoshang-windows-x64.update.json；传齐后再发布。不要使用 GitHub 自动生成的源码 ZIP。
4. A 进入首页检查（同一款成功检查间隔至少 6 小时），空闲时有新版提示“立即更新”。匹配软件、分发编号、平台、标签及递增版本，先验签，再核对 ZIP 长度、SHA-256、内层签名和每个运行文件；不执行包内安装脚本，不使用第三方更新镜像。播放、下载队列或本地媒体任务进行中暂缓，不自动暂停任务。选择“稍后”不会永久跳过该版本。
5. 新版放入 Windows 当前用户的独立更新缓存。固定入口和旧版不覆盖；试启报告首次界面就绪后才原子切换生效版本。下载、校验、解压或试启失败不覆盖旧程序；之前的完整运行目录保留。默认下载和日志仍以固定入口为基准，不回滚或搬动用户视频、记录、下载索引或授权。离线不依赖更新服务，许可证仍按原规则独立校验。

本版已构建红果赏、真果赏两个 Windows x64 运行目录，逐文件重新校验分发签名、运行文件摘要、公开密钥和分发编号。隔离验证包含两版签名发布→发现→整包校验→切换、占位地址零请求、忙碌拒绝、篡改/错误软件/旧版本/越界 ZIP 拒绝，以及真实 Windows 无界面子进程成功确认和崩溃回退；旧程序及模拟视频和记录保留。Flutter 授权/更新界面和固定路径定向检查通过。未操作正式软件窗口、真实用户账号或媒体；尚未配置真实更新仓库，未向 GitHub 发布或声称公网升级验收。GitHub 资产沿用脚本产生的安全文件名，例如 1.1.28-build159，版本与标签仍保留 1.1.28+159。

### Windows 1.1.29+160：新电脑登录与后续发布

授权连接默认使用本机网络；无代理直连，有明确的 HTTPS_PROXY/HTTP_PROXY 则按该环境配置，没有环境代理则使用 Windows 当前用户的代理、自动代理脚本或系统自动发现。保留绕过代理名单、HTTPS 证书校验和禁止授权跳转。不会修改电脑的网络设置。连接、DNS、证书或代理错误不计为错密；只有服务端拒绝账号验证时才计入 5 次 / 5 分钟保护，服务端 429 仍遵守 Retry-After。登录失败并不代表许可证未发放或已被停用，不需要为重试反复生成账户。

本次为 tag1.1.29，包内版本 1.1.29+160。旧包不会被覆盖。远端已装 1.1.28 的用户本次手动解压新包；从 1.1.29 开始支持 tag1.1.N（版本和构建号都受签名校验）。以后在项目根目录执行 python scripts/release_windows_updates.py --next-from 1.1.29+160 --cn-mirrors，会将版本一次递增为 1.1.30+161，生成两款完整 ZIP 和两份 JSON，保存在 dist/windows/releases/tag1.1.30；后面每次使用当时的真实原版本号。此命令不上传，也不会修改已发包。若因构建失败而中断，保留当前新版本号，完成缺少的构建步骤后运行 python scripts/release_windows_updates.py；若一款资产已生成，用 --edition 选择尚未完成的另一款，不覆盖旧包。

本轮复现与验收：只保留 Windows 用户代理时，1.1.28 的授权客户端选择直连并在 12 秒超时；同机新客户端选择系统代理，实际读取服务元数据，两个公钥均一致。旧代码 5 次模拟 DNS 失败会记录为 5 次错密并等待 300 秒；新代码不记错密、不产生密码等待，仍不授予访问。对授权 POST，只有尚未取得连接且未交付请求时才允许因短暂连接中断在同一路由重新建连一次；收到 HTTP 响应、已提交请求、证书错误均不重放。授权页遇到网络错误会显示“检测授权连接”，只读取公开元数据，不提交凭据。两个最终 ZIP 已分别解压到全新目录，核对签名、完整包摘要和每个文件；实际成品授权 DLL 在只有系统代理的条件下均验证了线上服务身份。隔离的后台与两版原生客户端完成新账号登录和激活，未使用真实用户密码或绑定设备；两版各 18 项定向 Flutter 检查通过。第二台实体电脑的实际登录和窗口由用户手动验证。

### Windows 1.1.30+161：手动检查更新

两款软件从指定公开仓库的 Releases Atom 订阅读取实际发布的 tag1.1.N，按版本数字比较，包括已公开的预发布，不再请求匿名 GitHub REST API。订阅暂时不可用（传输故障、404 或一般 5xx）时最多读取一次同一仓库的发布网页；真正的拒绝、明确限流及 Retry-After 不轮换线路、不伪报为最新。检查默认使用本机网络和系统代理，也保留各软件显式指定的直连或手动代理。无需登录 GitHub 或配置令牌。遇到错误，可在“关于 → 检查更新”的提示中手动打开发布页。

只有发现更高版本时才读取对应软件的更新签名清单；不依赖 ZIP 的 HEAD 探测。用户点击“立即更新”后才下载 ZIP，按原规则核对完整包大小、SHA-256、软件身份和包内签名，不通过就不切换。Windows 主程序的可选参数 --check-release-channel 在签名交付目录执行只读渠道检查，不启动窗口或下载更新。对外发布 tag1.1.30 时上传两个完整 ZIP 与两份签名清单，最终用户只需对应软件的 ZIP。

本轮核对区分两版：用户在另一台电脑看到红果赏 1.1.29 正常显示最新、真果赏报 HTTP 403。隔离对照复现了匿名 REST 在两种响应下的差异；1.1.30 两版均不请求 REST，阻断该 API 仍可从仓库订阅判断是否有更新。两个最终 ZIP 在不同空目录提取，实际主 EXE 均在无窗口模式读到了线上 tag1.1.29；以 1.1.28 为起点分别核对了线上 1.1.29 的两份真实签名。另以本地模拟发布向更新器提供实际的 1.1.30 ZIP 和签名，两款均能从 1.1.29 验签、下载并暂存正确的软件包。没有上传 1.1.30、切换正式软件、操作用户窗口或改动许可证、视频与记录；另一台电脑的 GUI 更新由用户手动验证。
